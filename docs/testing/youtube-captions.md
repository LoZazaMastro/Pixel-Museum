# Automatic film captions

The museum requests matching captions in its selected language, including English authored captions or automatic English transcription. `Video::caption_language(locale)` may be called before playback starts or while a film is playing. `caption_text()` returns the cue for the decoder's current clock, including after a seek; it returns an empty string for idle or failed playback, ended films and audio-only soundtrack tracks. `caption_status()` reports `off`, `waiting`, `loading`, `ok`, `unavailable` or an explicit error.

Selection first looks for a track in the chosen language, preferring an authored track over an automatic track at the same language specificity. An exact regional code takes priority over another variant of that language. Translation is requested only if the player explicitly marks a source track translatable and advertises the destination language. The caption URL retains its signed fields; `fmt=json3` is selected, stale translation parameters are removed and `tlang` is added only for an actual translation. A missing translation offer does not silently become English subtitles. Metadata from fallback media clients is retained because one client can expose a caption capability that another omits.

The implementation follows the fields in the current [YouTube.js caption parser](https://github.com/LuanRT/YouTube.js/blob/main/src/parser/classes/PlayerCaptionsTracklist.ts) and the language-selection behavior in [yt-dlp's YouTube extractor](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_video.py), inspected on 20 October 2026. Google's [caption-download documentation](https://developers.google.com/youtube/v3/docs/captions/download) explains `tlang` as machine translation; its separate authenticated editor API is not called here. The museum uses only caption URLs offered by its existing YouTube player metadata.

## Bounds and cancellation

One worker owns one active transfer and one replaceable pending request. Opening another film, changing language or closing playback invalidates the generation and clears visible cues immediately. A stale response cannot publish dialogue. Each transfer is limited to 2 MiB and an eight-second HTTP timeout, with cancellation checked during incoming chunks. A bounded sequence tries the offered JSON3, WebVTT and srv1 formats plus alternative client tracks in the same requested language (at most 12 requests). HTTP 429 stops the sequence rather than repeating a rate-limited request. Work runs separately from decoding and the frame thread. Shutdown can wait for the remaining bounded HTTP timeout. Empty HTTP 200 responses do not count as success. WebVTT and srv1/srv3 XML preserve cue timing and decode text entities; unrelated HTML is rejected. Request User-Agent follows the player client identified by the caption URL.

Parsing accepts at most 12,000 cues, 2,048 UTF-8 bytes per cue, 1 MiB of total retained cue text and 32 caption windows. Invalid, negative, non-finite or unreasonable timings are skipped; oversized or unsupported tracks fail explicitly. Overlapping replacements in the same window end the earlier cue, while supported append events extend that window's text. Start times are inclusive and end times exclusive. Neither playback gain nor soundtrack audio handling is changed.

## Verification

- The focused C++ test passed **32 checks**, including the actual InnerTube parser, direct versus translated selection, advertised capabilities, signed URL preservation, malformed input, timing boundaries, forward/backward seeks, window replacement, append events, cancellation, stale-result rejection, one-worker concurrency, HTTP 403 and response-size limits.
- The main host preview passed **30 caption-rendering cases at 3840 × 2160**, covering four languages, framed/fullscreen presentation, picture bounds and captions remaining visible when control hints hide. OpenGL reported no errors. These rendering checks use known dialogue fixtures.
- Native compile, link and conversion passed. `build/eboot.elf` SHA-256: `8d5d0e7d8782e16a8151c387432efb272299aec4c3c45475d1e4cc45b5a972b6`. The existing staged payload was not overwritten.

A bounded anonymous live metadata probe also succeeded for both official exhibit films. Brookhaven's `u6mu5B-YZU8` exposed one English track and 156 translation targets, including Italian. Digital Eclipse's `IrS2pipZaH0` exposed 21 tracks, including a direct Italian track, and 156 translation targets. The corresponding caption transfers did **not** demonstrate successful live subtitle playback: Brookhaven returned HTTP 429 and the direct Italian trailer request returned HTTP 200 with an empty body. Both results are treated as unavailable captions rather than successful playback. The local diagnostic is `build/caption-live-probe.json`; signed track URLs are not printed in logs or packaged as content.

Automatic translation is therefore best effort, dependent on the video's caption offers and YouTube accepting the caption request on the active connection. The backend, failure handling and native build are verified locally. Actual translated caption playback on PS5 remains unverified; this change has not been deployed to the running console.

## Current correction

English no longer disables subtitles. The selection retains other offered client tracks in the requested language, so a rejected or empty track does not exclude every other caption offer. Local checks now cover 40 cases, including actual VTT/srv1/srv3 data, UTF-8 entities, empty JSON3 fallback and replacement-client fallback. Captions are drawn outside the transient controls opacity and continue to appear after button hints fade.

The previous live-service result above remains a limit on what is verified. YouTube can require a caption-specific proof token or refuse timedtext on a connection. Trying another supported representation does not guarantee bypassing that service requirement; a fresh on-console subtitle test is still needed.

## 21 October: translation refusal and explicit source fallback

A fresh anonymous live probe reproduced the reported language difference on Brookhaven `u6mu5B-YZU8`: the offered original English JSON3 returned HTTP 200 with 10,865 bytes and nonempty timed dialogue. The same English source with `tlang=it`, `es`, `fr` and `de` each returned HTTP 429. No translated body was received. These four translations are **not verified working**; changing renderer or treating the English response as a translation would not resolve the service refusal. Sanitized receipts and the original English body are in `build/research/captions-live`; signed URLs are not included in the receipts.

Selection now prefers an offered English source over another source language when requesting automatic translation. The chosen museum locale remains unchanged during failure. A rejected/empty target can use an offered original-English caption track only as an explicit fallback: loader status is `fallback: en`, and the film controls say `English subtitles / translation unavailable`. This status never reports successful Italian, Spanish, French or German subtitles. A translation HTTP429 stops further translated formats/client retries; only the separately offered English fallback is attempted, with the overall twelve-request limit retained. Cancellation and language changes still invalidate all old cues.

The focused host suite passes 54 checks, including four target parameters retained through actual loader requests, English-source preference, one translated request after rate limiting, explicit fallback status, generation cancellation and cue timing. Network acceptance of translated captions remains an external pending condition; no PS5 translation success is claimed.

A further selection regression retains an English-source translation candidate even when many clients advertise the same direct target-language track with empty bodies. English viewing retains its alternative direct-client tracks. The fallback keeps the selected museum locale intact.
